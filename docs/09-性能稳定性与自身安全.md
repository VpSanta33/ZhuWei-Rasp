# 第 9 章　性能、稳定性与自身安全

> RASP 项目成败的关键不在“能检测多少攻击”，而在于“业务愿不愿意装”。本章的要求是硬性约束。

## 9.1 性能预算

| 环节 | 预算 | 手段 |
|---|---|---|
| 无请求上下文、未命中检测的 Hook 调用 | < 1μs | Spy 快速判断开关；hookId 用数组索引分派 |
| 单次检测（常见情况） | < 50μs | 先判空/长度/白名单；输入预处理结果缓存在请求上下文中 |
| 单次检测（P99） | < 1ms | 限制输入数量和长度；正则预编译并限制回溯 |
| 调用栈获取 | 仅在需要时 | 栈懒加载；使用 `StackWalker`（JDK 9+）并限制深度（默认 50 帧） |
| 启动 | < 10s | 只对匹配类做转换；类名快速前缀过滤 |
| 内存 | < 100MB | 有界队列；body 缓存上限；规则对象共享 |

**必须避免的写法**：

- 在 Hook 中 `new Throwable().getStackTrace()` 且每次都执行。
- 在 transform 中加载业务类（`Class.forName`）。
- 在 Hook 中加锁或做同步 I/O（日志也必须异步）。
- 使用回溯不可控的正则。
- 无界的集合/队列/缓存。

## 9.2 熔断与自监控

`rasp-monitor` 线程每 5s 采集一次：

- Agent 线程 CPU 时间（`ThreadMXBean`）+ Hook 耗时累计（由检测代码统计，使用 `LongAdder`）。
- 检测耗时分位数（使用 HdrHistogram 或简化的分桶统计）。
- Agent 内部异常次数。
- 告警队列丢弃数。

熔断状态机：

```
CLOSED ──(连续 N 个窗口超阈值)──► OPEN（关闭全部检测，只保留心跳）
  ▲                                │
  │                         (冷却 recover_sec)
  │                                ▼
  └────────(指标正常)──────── HALF_OPEN（按 10% 采样开启检测）
```

- 阈值来自 Server 配置（第 7 章 `breaker`）。
- 熔断事件上报到平台并告警。
- 还有一类**单点熔断**：某个 Hook 在一个窗口内异常次数超过阈值，就只关闭该 Hook。

## 9.3 稳定性红线

1. **所有 Agent 代码路径都要 catch `Throwable`**（阻断异常除外），并且不能往业务抛出。
2. **不改变业务语义**：不提前消费请求体，不改变参数解析顺序，不修改响应（阻断时除外）。
3. **不造成死锁**：Hook 内不持锁调用外部代码；类转换阶段不触发类加载。
4. **不造成 OOM**：所有缓存/队列有上限；大字段截断；ThreadLocal 在请求结束时清理。
5. **防递归**：Agent 自身执行期间设置 `inRasp` 标志，跳过所有 Hook。
6. **与其他 Agent 共存**：要和 SkyWalking、Pinpoint、Arthas、JaCoCo 等常见 Agent 一起测试；Transformer 只做增量修改，不覆盖别人的修改。
7. **失联无影响**：Server 不可达时，业务性能和行为不受影响。

## 9.4 自身安全

| 风险 | 措施 |
|---|---|
| 攻击者通过反射修改 RASP 开关、卸载 Hook | core 位于独立 ClassLoader，类名经过 shade；关键开关字段不对外暴露；对 `Spy` 类的反射访问可以检测并告警（`Field.set` Hook，可选） |
| 伪造/篡改下发策略 | 策略签名（MVP 已实现）：Server 用 ECDSA P-256 私钥签名，Agent 用 `rasp.properties` 中固定的公钥 `policy.public_key` 验签；绑定 `app_key`，`issued_at` 防回滚；失败保留旧配置并告警。传输层 HMAC 只证明“Agent 是谁”，签名证明“策略确实来自平台” |
| 伪造规则包 | 规则包使用签名（与策略签名同一套密钥体系），公钥内置在 Agent 中 |
| 伪造 Agent 上报垃圾数据 | HMAC 签名 + 限流 + 字段校验 |
| 中间人 | 强制 TLS 并校验证书；可选证书固定 |
| 敏感数据泄露 | 上报前对 Cookie、Authorization、密码类参数脱敏；body 截断；平台侧按权限展示 |
| 平台被入侵 | 平台本身做安全加固：RBAC、审计、MFA、控制台不对公网开放；“下发 block 配置”属于高危操作，要求二次确认 |
| 本地文件被篡改 | 安装目录权限设为 root 只读（Agent 只写 logs/rules 缓存）；配置缓存 `cache/config.json` 保存签名信封，启动时重新验签 |

### 9.4.1 平台侧已实现的防护（MVP）

| 风险 | 措施 |
|---|---|
| 控制台口令爆破 | 按 IP 与用户名计数，15 分钟内 10 次失败锁定 15 分钟；失败登录写审计并计入指标 |
| 数据库泄露 | 口令 PBKDF2 哈希；会话与 API Token 仅存 SHA-256；数据库文件 600；备份文件 600 |
| 越权操作 | 三级角色，写操作默认至少 operator；只读用户看不到 App Secret |
| 签名私钥泄露 | 私钥对其他用户可读时平台拒绝启动；备份时单独拷贝并保持 600 |
| 告警洪泛拖垮平台 | 每应用令牌桶限流，超出丢弃并计数；阻断事件优先保留 |

平台容量实测数据见第 13 章 13.6。

## 9.5 隐私与合规

- 告警数据可能包含个人信息，需要遵守公司数据分级要求：默认脱敏，原文查看需要授权，并记录审计。
- 数据保留期可配置，到期自动删除（ClickHouse TTL）。
